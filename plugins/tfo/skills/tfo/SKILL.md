# TaskFlow Orchestrator: engine and Bootstrap

This plugin bundles a conventional local supervisor and the Bootstrap development workflow. For new native Codex coordinations the principal stays active, makes decisions and integrates; TFO stores checkpoints and verifies completed worker turns. Its supervisor observes and recovers verified failures. It uses no separate AI agent. Node.js 20+ is required; local Codex execution also requires Codex CLI. The local RC includes a private web MCP entry for preparation, while automatic delivery on ChatGPT surfaces remains unverified. Use the `tfo_*` tools.

## Opciones efectivas y comunicación

Lee `tfo_settings` antes de preparar trabajo nuevo. Valores de instalación nueva: Automático, Permitir siempre, Inteligente Normal. La migración conserva las preferencias previas. Consulta [modos y permisos](../../docs/SMART_MODES.md) para los ocho perfiles, Custom y el contrato de medición.

Al instalar o inicializar, explica brevemente para qué sirve y sus opciones efectivas. Durante planes o ejecución menciona la utilidad concreta y después los chats o prompts realmente coordinados. No repitas una presentación general sin que se pida.

Respeta `usagePolicy` y `permissionPolicy`. Usa `tfo_work_prepare` cuando deba resolverse una elección antes del plan ejecutable; conserva su `workId`. Si la persona ya aceptó TFO para este trabajo, `usageAccepted:true` registra esa elección. `planAccepted:true` solo cuando se aceptó el plan. Un permiso pendiente se concede en Opciones con alcance de proyecto/cadena o global; no pulses Permitir en nombre de la persona. No preguntes por cada prompt. Un estado pendiente no autoriza envíos.

La IA evalúa cada tarea: registra una referencia `normalSelection`, la recomendación `selection` y `selectionReason`. No lances otro modelo para calcular Normal. Normal admite los tres modelos sin cuotas; Ahorro minimiza coste total incluidas correcciones; Rápido y MaxSpeed priorizan velocidad de manera progresiva con coste contextual; Calidad sube un nivel de modelo con la misma potencia; Máximo busca ganancias perceptibles y puede conservar Luna alto. HQ y MaxHQ añaden revisión independiente. Custom fija modelo y potencia en los nuevos turnos, incluido el maestro.

No subas Ultra por defecto ni atribuyas una velocidad medida a la potencia. Verifica el catálogo real. Calidad conserva potencia aunque el modelo cambie; TFO calcula la subida desde Normal. Las tareas inline del principal deben coincidir con su turno real: para un principal Astra en Calidad, la referencia puede ser Sol a la misma potencia. Custom incompatible requiere un turno nuevo, no una afirmación de cambio a mitad del turno.

HQ/MaxHQ añaden un revisor de solo lectura tras la integración. Lee su resultado; ante defectos conserva el recibo, agrega correcciones y una revisión posterior, y mueve el cierre final tras ella mediante `tfo_native_revise`. La revisión debe cubrir todas las tareas. No conviertas una cola de un chat a HQ: necesita un flujo independiente de revisión. Tras un cambio expreso de modo para el trabajo, revisa tareas pendientes; nunca reescribas intentos ya enviados.

Las opciones globales afectan a trabajos nuevos. Deshabilitar bloquea todos los envíos nuevos, incluidas recuperaciones. Una concesión revocada bloquea los trabajos que dependan de ella. TFO conserva evidencias y nunca reenvía un intento incierto.

## Identify the product before starting

In normal Chat or ChatGPT Work, first call `tfo_connection_check` with `surface: "chatgpt-chat"` or `"chatgpt-work"`. For local Codex use `"codex"`. The product is caller-declared, not discovered by this tool. Never infer it from a UUID, model label, or a local folder. `tfo_connection_panel` renders a read-only MCP Apps diagnostic in supported chats. It never sends a prompt. Tool connection, UI rendering, autonomous sending and actual model selection are separate gates.

If these tools are absent, say that the MCP connection is unavailable in this chat. A plugin mention or loaded skill alone is not a working connection. Do not replace it with separate agents, an App Server writer or self-directed host messages. Preserve the user's requested Chat mode and visible effort label; do not silently map it to a Codex model/effort. Keep proposed work as a plan until its host adapter is available and verified.

### Principal activo con herramientas nativas de Codex

Use tfo_native_* for new local Codex project coordination. coordinationMode defaults to active_main: THIS principal keeps its current turn active, dispatches each returned native action once, waits through tfo_native_wait, verifies results and adapts the plan. The principal integrates in the same turn and alone performs authorized commits, pushes and draft PR creation/update. Worker results never grant extra authority. Do not send a self-message to coordinate, change model mid-turn or open a second App Server writer.

1. Identify the real source chat, native project and actual selection. Read the captured work policy and assess every task inside its explicit limits. Prepare nodes and lanes with tfo_native_prepare. The worker cap is 1-100 (persistent default 2), up to 100 lanes and 1,000 tasks. This is not a guarantee of host slots. An explicit per-run limit overrides the persistent default; only an explicit user instruction permits raising a live limit.
2. Use verified Git worktrees for writes. The first native Git create_thread action provisions a separate worktree with a read-only bootstrap. Wait for real completion of setup, then acknowledge the real threadId and workspace; never acknowledge clientThreadId or allow edits before isolation verification. Scratch folders must remain separate and outside Git.
3. Claim a ready worker node, execute exactly the returned create_thread or send_message_to_thread arguments once, acknowledge and observe. A pending capacity response is not a dispatch authorization. Never resend an attempted native action. Workers keep edits local and cannot publish or take over coordination. Ordinary subordinate workers do not open other chats. An explicitly authorized independent master (for example one master per benchmark configuration) may coordinate its own flow; do not misclassify it as a subordinate worker. Only a structured host rejection with code HOST_CAPACITY and deliveryAttempted=false proves that a dispatch did not happen: pass it to tfo_native_defer_dispatch to preserve the attempt and return the task to pending. Free-form errors, interrupted calls and missing receipts never prove no delivery and must remain in review without a retry.
4. Wait using tfo_native_wait(runId,afterCursor,timeoutMs), at most 60 seconds per call. Preserve nextCursor and drain hasMore. The observer returns at most 20 compact events and catches all lanes; do not poll every few seconds or fetch all reports on each continuation. Use tfo_native_results by nodeId for full evidence, or page for groups of 20 summaries.
5. Adapt within the authorized objective using tfo_native_revise with expectedRevision. Add lanes/nodes, replace only unattempted nodes, and map a verified blocked result to its remediation through resolveBlocked. Preserve attempted work. Do useful principal work while workers run and record it using tfo_native_checkpoint; this is not a final host receipt.
6. Verify required work and integration checks, then call tfo_native_finish. Include the exact returned mainCompleteMarker in the final answer and END the turn. The independent observer verifies that final source receipt before completing the flow and releasing reservations. Attach each created draft PR through native attach_artifact.
7. Pause prevents future dispatch and recovery. Cancel drains attempted turns and preserves results. Reconcile uncertain delivery through tfo_native_reconcile, which never sends. Resume does not clear uncertain actions. The principal adopts verified recovery with tfo_native_recover and reads preserved state rather than replaying workers.

The durable observer restores on MCP startup with one process owner. It may recover an inactive failed or prematurely completed principal at most THREE times per whole flow, delayed 1, 3 and 10 minutes after successive verified failures. It persists intent before each unique recovery prompt and verifies actual delivery/selection. Active waits, user pauses and ambiguous interruptions never trigger recovery. Missing host access preserves state. Uncertain attempts or an exhausted budget require review, not another automatic prompt.

Before publishing an authorized milestone, the principal reviews the exact diff, integrates only its files/commits and checks the result. Keep the branch being integrated or published reserved from concurrent worker writes. Stage only reviewed files; inspect any expanded scope before including it. Record branch, reviewed files, tests, published commit IDs and draft PR URL in the principal checkpoint evidence, and attach the PR to this chat. Publication ends at the draft PR; merge requires a separate explicit user authorization.

Saved flows without active_main keep their previous semantics. Explicit deferred_join uses the prior inactive-source final handoff: same-selection native queue, or guarded visible composer for changed selection. Finish the source turn with the returned mainJoinMarker before that handoff. Its worker continuations still need a native-tool caller; new active coordination does not use that return path. Live acceptance of the new recovery/worktree path must be reported separately from fixtures.

When the MCP process is stale after an update, runtime/native-flow-control.mjs supports the same prepare/claim/acknowledge/defer_dispatch/observe/status/revise/checkpoint/finish/wait/results/pause/resume/cancel/reconcile/recover operations with a JSON input file and the same TFO_DATA_DIR. It is the same engine and transport, not another writer.

### Model selection applies to every orchestrated turn

Before dispatching ANY prompt, assess the task and record a justified model/effort selection within the user's profile and limits. This applies equally to creating a chat, continuing it, dependent tasks, integration, and the next turn of THIS principal chat. Being the principal is never a reason to inherit its previous selection. The conversational AI estimates difficulty, risk, context and verification needs; TFO persists, applies and verifies the choice. These are explicit heuristics, not a calibrated optimum or a promise of savings.

Keep source selection (used to verify the previous turn) separate from requested task selection. Verify the observed model/effort from the actual new turn receipt. If the required transport cannot apply the requested selection, stop before sending with a clear unsupported-selection reason; never fall back silently to inherited selection or another writer. A selected-main adapter tested only with fixtures is not a live host capability. Do not modify a model mid-turn. A user intervention during orchestration needs reviewed recovery with saved results and no duplicate sends, not a blind restart.

Use `gpt-6.1-sol` for every new automatic Sol-tier choice. Use `gpt-6-sol` only when the user explicitly requests that exact older model; an observed source model, stale example or previous automatic recommendation is not such a request. Preserve exact observed source IDs, historical receipts, explicit user selections and already approved immutable plans. Never rewrite them to 6.1. If the host cannot use 6.1, report unsupported selection rather than fall back to 6. For Intelligent Normal, evaluate bounded tasks, dependencies, context and verification needs independently; choose Luna, Sol or Astra without predetermined proportions. Sol 6.1 occupies the Sol tier alongside GPT-6 Luna/Astra, not a separate generation requiring cross-family escalation. These are routing preferences, not a claim that one model wins every benchmark. The Codex host catalog supports low through ultra for 6.1 here; the public API catalog is separate and must not be used to infer Codex effort availability.

### Choose task size and capacity

Respect the user's maximum parallel chats and model/effort ceiling. For a low-cost request, group tiny dependent edits into one turn unless the user is testing transitions. Prefer Luna low for clear, easily checked edits, Luna medium for bounded tasks, and GPT-6.1 Sol medium for coding whose dependencies need reasoning. These are starting heuristics, not calibrated quality predictions. Use only supported host pairs; failures never authorize an expensive fallback. Record a reason for each choice, and raise effort/model only within the user's authorized plan. Keep independent chains in separate chats, preserve short useful handoffs and account for system/tool context repeated by every model call.

Budget estimates are uncalibrated API equivalents with explicit assumptions, not Codex quota, time predictions or promised savings. Compare measured completion, validation, elapsed time, input/cache/output/reasoning tokens and dispatch overhead. One tiny test cannot calibrate IGTAP performance; report missing data instead of inferring it. Short-context standard prices are a reference, and other processing tiers or long contexts may differ.

### Compatibility: saved deferred coordinations

Existing `tfo_parallel_*` and storage-only `tfo_project_*` executions keep their original rules, receipts and recovery controls. Read status before resuming. Do not create new work through their retired prepare entries. A deferred flow waits for worker completion and an idle source turn; active coordination instead integrates inline. Preserve workspace reservations and exact receipts. Pausing prevents new sends while collecting active results; cancelling drains existing sends and retains files. Uncertain delivery requires reconciliation, never blind retry. See [coordination](../../docs/PARALLEL_CODEX.md) for historical transport details.

For private web setup, use bundled `runtime/web-server.mjs` through Secure MCP Tunnel as described in `docs/WEB_PRIVATE_SETUP.md`. This does not require public publication. Never tunnel `runtime/server.mjs`, which exposes local execution tools. Never ask the user to paste keys in chat. A successful `tfo_health` must report `profile: "private-web"`. Then use `tfo_web_prepare` for an authorized plan with the real conversation URL, exact requested model/effort labels and one request UUID retained for retries; use `tfo_web_panel`, `tfo_web_status` and `tfo_web_cancel` to inspect or cancel it. `Chat` is a mode, not a model name. A prepared queue is `awaiting_host_adapter`: no prompt was sent and no turn or selection was verified. The local entry's web support remains diagnostic only.

Never claim workers have started merely because the plan names them.

## Store a queue and let TFO wait

For this supervised development, prepare the queue paused and ask the user to leave the target chat visible, its composer empty and keyboard/mouse available. Wait for the actual answer before activation; do not expire the question by immediately ending the turn. One confirmation covers the stored sequence, not an automatic retry after failure.

When this chat still exposes an stale MCP process after a local update, use the packaged `runtime/queue-control.mjs` fresh-process entry with JSON on stdin. `prepare` always persists a paused queue; `resume`, `status` and `cancel` accept `{ "runId": "queue_..." }`. It uses the same conventional supervisor and safety guards, never a second App Server. Preparing and observing must use the same `hostObservationVersion`; a missing/different revision stops startup. Do not edit a failed queue's count to make it pass. Preserve the failure, then prepare the remaining authorized work with the corrected entry. Native delivery retains the current selection; selection changes still require guarded UI. Include the queue ID in every queued turn's final answer so the next dispatch can identify the visible chat.

Use `tfo_queue_start` when the user wants several prompts run one after another. This is the preferred conventional supervisor: it stores every prompt and explicit selection before returning, waits for the preparing turn to finish, sends one prompt, and waits for the host's final response before advancing. It has no model or separate agent. Do not use `send_message_to_thread` to imitate this queue during the active answer, and do not ask the user to type "continue" between steps.

1. Read `tfo_health`, the current host selection and `tfo_ui_diagnostic`. An stale MCP connection does not gain new tools merely because the plugin was reinstalled. If the installed process cannot observe the desktop, report that prerequisite without sending test prompts through another writer.
2. Store `threadId` for THIS chat, the authorized `projectPath`, an `initialSelection` matching the actual current turn, and 1–20 steps. Each step has `prompt`, `selection: {model, reasoning}` and optional `expectedResponse`. Expected responses compare the final answer, not commentary. Without an expected response, the checkpoint confirms turn completion only, not correctness of the work.
3. For historical queues only, `allowPlannedIncreases` may be true only when the user explicitly approved that precise selection sequence, such as Luna medium → low → medium. This permission is stored with the immutable queue and normally cannot exceed the initial selection. If the user explicitly requests exact model/effort pairs above the current selection, list only those pairs in `authorizedSelections`; each must appear in a stored step. The initialSelection must still match the actual current turn. This per-queue exception never permits other pairs or another model generation. It does not change global settings.
4. Include the returned queue ID in your final answer and END the turn. Do not wait inside the AI turn, send a control prompt, or call completion tools for this queue. The tool must return a live supervisor with `launchMode: prestarted` and an owner PID. It starts from an immutable runtime snapshot while the source turn is active, acknowledges startup, then waits for the completed-turn record. `Stop` is auxiliary for these queues; it cannot start a second dispatcher. The supervisor verifies chat identity, empty composer and selection before one send attempt. A startup failure is `needs_review`, never a promise that the hook will start it later. It continues watching after sending, so a short answer like "hola" needs no AI bookkeeping.
5. The supervisor checks the exact prompt, real turn ID, model/effort, final response and completion event before saving a checkpoint. Duplicate Stop signals cannot create duplicate sends. Extra user input, interruption, unexpected selection/answer or ambiguous delivery stops for review. Pause/cancel through `tfo_queue_*` or Options. A restart retains the queue and pauses for review; uncertain sends are never retried.

If a send is marked uncertain after the UI action, inspect the host history first. `tfo_queue_reconcile` is a no-send repair: it records a checkpoint only when the exact route-marked prompt appears in exactly one turn started after that attempt, and that turn is complete with the requested model, effort and expected final response. If prompts remain, reconciliation leaves the queue paused. Never resume or resend just to clear an uncertain status.

An earlier beta's live attempt stopped in read-only preflight because the route marker was not visible. No prompt was confirmed. A later beta distinguishes that failure from an uncertain send. Live desktop delivery and model switching still require verification; never call the MVP ready based on simulated tests alone. Hook trust is controlled by Codex and must not be bypassed.

The guarded UI path confirms the exact submitted prompt and turn ID; the host may write its `turn_context` later, so actual model and effort are checked against the completed receipt before the step is accepted. The read-only diagnostic reports `readinessChecked: false`; do not interpret that as a disabled engine or a completed send preflight. A valid Stop event records metadata under the local data directory's `hook-signals/<threadId>.json`, independently of whether a queue exists. Installing the plugin is not evidence that the host ran its hook.

## Run a route with AI checkpoints

1. Call `tfo_health` and `tfo_settings`. For budgeted routes, also call `tfo_catalog` and `tfo_preview`. Before the first accessibility dispatch, call `tfo_ui_diagnostic`; it only reads whether the installed process sees one Codex Desktop window, its composer and selector. If an older engine answers, treat the updated tools as unavailable in this chat; do not assume they are active.
2. Use the user's authorized objective, project folder and constraints. Existing authorization remains valid. Present a concise route only when scope or choices still need agreement.
3. Call `tfo_budgeted_chat_start` with the **current chat** UUID, real project path, objective, 1–20 steps and `initialSelection: {model, reasoning}` matching the host's actual current selection. The tool saves the first prompt as pending. Include its run ID in your final response so the local supervisor can bind the visible chat, then end your answer. The supervisor may select a different model or effort through the accessible Codex interface only after verifying that it is idle, this route is visible and the editor is empty. If that interface is unavailable, this route stops before sending. Never invent a higher ceiling. `tfo_chat_start` remains for compatible routes without the new budget gate.
4. Each step needs a complete, natural-language `title` and `prompt`, with acceptance criteria. The engine adds prior results, scope and checkpoint instructions.
5. Assess suitability using `assessment: {complexity, confidence, reason, recommendation?}`. Complexity is `routine`, `standard` or `complex`; confidence is `high` or `low`. A confident routine assessment can select GPT-6 Luna low. A recommendation is `{model, reasoning}`. Without a confident assessment the engine preserves the current level. Consider the entire remaining sequence before lowering: later steps may need the current capacity.
6. The supervisor receives the Codex `Stop` event, confirms that the source turn completed, and checks the accessible interface before sending. At each step, read status before working; stop on pause, cancellation or review. Save its outcome using `tfo_chat_complete` with `runId`, `stepId`, `success`, and a factual `summary`. Optionally include `nextAssessment` for the next step. The engine saves the checkpoint and next prompt as pending. Include the run ID in your final response and end the turn. Verify each turn's actual model; an intended selection alone is not evidence.

Do not imitate the queue by printing an internal prompt. Do not claim delivery or an effective model switch from intent alone. Dispatch records identify the requested model; the next turn's host metadata is evidence of actual use.

## Opciones, límites y registros

Usa `tfo_options` para el panel local; ábrelo en un panel lateral si el usuario pide las opciones o necesita resolver una elección. El host puede mostrar también `tfo_settings_read`/`tfo_settings_update` como opciones nativas. Ambos usan los mismos valores. Custom solo ofrece modelos y potencias verificados en el catálogo. Nunca operes una concesión del usuario ni evadas una restricción del host.

Las reglas descendentes de ahorro y sus autorizaciones exactas se conservan únicamente en ejecuciones históricas. En trabajos nuevos la IA puede subir o bajar entre tareas según el modo y los límites capturados. Un cambio global no altera una ejecución existente; un cambio explícito del trabajo afecta solo a tareas pendientes.

Usa `tfo_measurements` para exportar evidencia sin prompts ni respuestas. Distingue tiempos observados, tokens disponibles, dólares equivalentes de API y cuota de suscripción. Calidad y métricas ausentes permanecen sin valor; no inventes puntuaciones ni ahorro medido. La comparativa Defold y el piloto requieren elegir antes el proyecto con el usuario.

No crees trabajos nuevos con `tfo_start`, `tfo_project_prepare` ni `tfo_parallel_prepare`: son entradas históricas retiradas. Los controles de ejecuciones anteriores siguen disponibles. Usa coordinación nativa para proyectos y colas para prompts en un mismo chat.

## Interruptions and recovery

Read status first. Resume only a paused route; it preserves an already queued message. A failed step or uncertain delivery enters `needs_review`; inspect the conversation and saved results before constructing a corrected remaining route within the user's authorization. Never resend blindly. Cancelling does not undo file changes.

## Develop TFO with Bootstrap

Treat the user's open repository as the source of truth. Read its `AGENTS.md`, README and release-readiness guide, then relevant architecture documents. Inspect Git status before editing. Keep work within the user's scope and quota preference.

Canonical engine code is in the repository's `runtime/`; `plugins/tfo/runtime/` is generated by `node scripts/build-plugin.mjs`. Rebuild after engine edits. Keep local and portable manifests consistent. Test a candidate and preserve the previous runnable package before promotion. During bootstrap, promotion requires user authorization; a request to update/install the plugin already supplies it.

Local packaging currently uses `.codex-plugin/plugin.json`. Never restore a root `plugin.json` in this local package: the installed host selects AgentPlugin format and silently omits its hooks. Keep the portable export as `plugin.portable.json`. After installation, query `hooks/list` read-only to confirm the Stop hook is discovered and its trust status; this does not require loading or resuming any chat. An `untrusted` result requires the user's normal hook review in Codex. Do not modify trust hashes, use bypass flags or manually invoke Stop to simulate host approval.

The conversational AI owns planning and judgment; TFO owns checkpoints, scheduling and model limits. Do not expand permissions or infer approval for destructive actions or publication. Explicit Git backup authorization in the conversation remains valid. Use the connected GitHub integration if Git Credential Manager is broken; do not repeatedly launch authentication windows.

The handoff should state what works, what was verified, what still needs a live host check, where the recovery copy is, and how to continue. A local plugin install does not publish it to a public directory.
